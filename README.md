# eltex-automation

Автоматизация коммутаторов Eltex MES по SSH через [netmiko](https://github.com/ktbyers/netmiko):
снятие конфигурации, инвентаризация состояния, массовая настройка.

**Статус:** бэкап конфигурации парка работает и проверен на реальном парке коммутаторов MES.
NTP настроен на всех устройствах парка. Разбор вывода и desired state в YAML — не начаты.

> Адреса и имена в репозитории обезличены и заменены на документационные
> (`192.0.2.0/24`, `198.51.100.0/24` — диапазоны из RFC 5737, специально для примеров).

## Что уже работает

| Скрипт | Что делает | Меняет конфиг |
|---|---|---|
| `scripts/capture.py` | снимает 4 команды с одного устройства в `out/<host>/` | нет |
| `scripts/backup.py` | бэкап `startup-config` и `running-config` со всего парка | нет |
| `scripts/setup_ntp.py` | прописывает NTP на весь парк и сохраняет конфиг через `wr` | **да** |

## Требования

- Linux (проверено на Arch Linux), Python 3.10+
- SSH-доступ к коммутаторам, порт 22; telnet выключен
- учётная запись с достаточными правами (`enable` на проверенных MES не требуется)

## Установка

```bash
cd eltex-automation
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

На Arch Linux установка пакетов в системный Python запрещена (PEP 668), окружение обязательное.
Версии прямых зависимостей зафиксированы в `requirements.txt` (`netmiko 4.8.0`, `python-dotenv 1.2.4`).

## Подготовка

Список устройств и параметры подключения не хранятся в репозитории:

```bash
cp inventory.example.txt inventory/devices.txt   # адреса своих коммутаторов
cp .env.example .env                             # хост и пользователь для capture.py
```

Оба получившихся файла исключены в `.gitignore`.

## Учётные данные

Пароль **не хранится на диске**: спрашивается через `getpass` при запуске и живёт только в памяти процесса.

| Что | Откуда берётся |
|---|---|
| адреса устройств | `inventory/devices.txt` (в git только `inventory.example.txt`) |
| пользователь | `-u/--user`, иначе запрос при старте |
| пароль | `-k/--ask-pass` или SSH-ключ `~/.ssh/eltex_backup` (`--key-file`) |
| хост для `capture.py` | `.env` (`ELTEX_HOST`, `ELTEX_USER`), файл вне git |

Для десятков устройств в будущем — внешнее хранилище секретов (pass / sops / Vault). Сейчас не нужно.

## Запуск

### Бэкап конфигурации парка

```bash
source .venv/bin/activate
python scripts/backup.py -u admin -k
```

| Опция | Назначение | По умолчанию |
|---|---|---|
| `-i/--inventory FILE` | файл со списком устройств | `inventory/devices.txt` |
| `-u/--user USER` | пользователь, иначе спросит | — |
| `-k/--ask-pass` | спросить пароль вместо SSH-ключа | ключ |
| `--key-file FILE` | приватный ключ | `~/.ssh/eltex_backup` |
| `-p/--port N` | SSH-порт | 22 |
| `-l/--limit HOST[,HOST]` | только перечисленные хосты (точные адреса) | весь инвентарь |
| `--list-hosts` | показать список и выйти, без подключений | — |

Что делает прогон:

1. Читает инвентарь (пустые строки и `#` игнорируются, дубликаты схлопываются).
2. Подключается, определяет имя устройства через `find_prompt()`.
3. Забирает `startup-config` и `running-config`, проверяет, что ответ похож на конфиг
   (длина ≥ 200 байт и наличие строки `interface`), иначе — ошибка устройства.
4. Только после успешного чтения **обоих** конфигов пишет файлы на диск.
5. Предупреждает, если `running-config` отличается от `startup-config` (несохранённые изменения).

Результат:

```
backups/<YYYY-MM-DD>/<hostname>_<ip>_<startup-config|running-config>.cfg
out/backup.log          общий лог прогона
out/<ip>/session.log    полный диалог с устройством
```

Итоговая строка: `ok=…, fail=…, skipped=…, total=…`.
`fail` — попробовали и не вышло, `skipped` — не трогали (например, после прерывания).
Код возврата `0`, если ошибок нет, иначе `1`.

Отладка на одном устройстве:

```bash
python scripts/backup.py -u admin -k --limit 192.0.2.10
```

> При отладке пароля поставьте `MAX_AUTH_FAILS_IN_ROW = 1`: три неудачных попытки подряд
> на боевом устройстве могут привести к блокировке учётной записи.

### Снятие вывода команд с одного устройства

```bash
python scripts/capture.py
```

Берёт хост из `.env`, спрашивает пароль, снимает `show session`, `show interfaces status`,
`show vlan`, `show running-config` в `out/<host>/`. Ничего не меняет.

### Массовая настройка NTP

```bash
python scripts/setup_ntp.py
```

**Пишет конфигурацию на все устройства инвентаря.** Применяет `clock timezone`, `clock source ntp`,
`ntp server`, ждёт 10 секунд, проверяет `show ntp associations` и сохраняет конфиг через `wr`.

Сервер, часовой пояс и пользователь заданы константами в начале файла:

```python
USER = "admin"
NTP_SERVER = "198.51.100.10"
TIMEZONE = "UTC +3"
```

Известные ограничения (первая версия):

- нет dry-run и гейта «сначала одно устройство» — идёт сразу по всему парку;
- при несинхронизировавшемся за 10 секунд времени печатает `ERROR: no ntp server`, хотя конфиг
  применён — сообщение называет не ту причину;
- конфиг в этом случае не сохраняется.

## Структура проекта

```
scripts/      скрипты: capture.py, backup.py, setup_ntp.py
inventory/    списки устройств: *.txt вне git, в репозитории только *.example.txt
backups/      снятые конфиги по датам (вне git)
out/          логи прогонов, сессии, снятый вывод (вне git)
secrets/      креденшелы (вне git; при getpass не нужен)
```

`.gitignore`: `.venv/`, `.env`, `out/`, `backups/`, `inventory/*.txt` (кроме `*.example.txt`),
`secrets/`, `__pycache__/`, `*.py[cod]`.

**`backups/` — это секреты.** В конфигах лежат хэши локальных паролей, SNMP community и прочее.
Каталог не должен попадать ни в git, ни в чужие руки.

## Особенности Eltex MES (проверено на MES3300)

- `terminal ?` показывает только `datadump`, `history`, `no`, `prompt`, `width`. Команды
  `terminal length` нет — приём `terminal length 0` неприменим.
- Пагинацию снимает `terminal datadump`; драйвер `device_type="eltex"` отправляет её сам
  при подключении.
- Неизвестная команда даёт `% Unrecognized command`. `send_command` и `send_config_set`
  при этом **не бросают исключение** — ошибку надо искать в тексте ответа либо проверять
  результат чтением конфига.
- `show running-config | include <текст>` работает как поиск подстроки: `| include ntp`
  вернёт и `clock source ntp`, и `ntp server ...`. При отсутствии совпадений вывод **пустой** —
  без заголовка и без ошибки.
- Имя порта пишется по-разному: `gi1/0/22` в `show interfaces status` и
  `GigabitEthernet1/0/22` в `show running-config` — нужен единый канонический вид.
- `save_config()` в драйвере netmiko для Eltex не реализован (`NotImplementedError`).
  Сохранение — команда **`wr`** (write memory), подтверждения не запрашивает.
- Драйвер `eltex_esr` — для линейки ESR: `configure` вместо `configure terminal`,
  приглашение `)#`, `commit/confirm/restore`. Для MES не использовать.

## Задача NTP: что и почему

Рабочий блок на устройстве:

```
configure terminal
clock timezone UTC +3
clock source ntp
ntp server 198.51.100.10
end
wr
```

Три места, где легко ошибиться:

1. **`clock source ntp` обязателен.** Без него `ntp server` пропишется, но источником времени
   останутся локальные часы: конфиг выглядит настроенным, синхронизации нет.
2. **Сохранение — `wr`,** а не `copy running-config startup-config`. Без `wr` вся работа живёт
   до первого ребута.
3. **`clock timezone` перезаписывает существующий пояс.** Массовое применение молча меняет
   часовой пояс там, где он был другим. Это должно быть осознанным решением, а не третьей
   строкой в списке команд.

Проверка распадается на два независимых вопроса:

| Вопрос | Команда | Когда есть ответ |
|---|---|---|
| Конфиг применён? | `show running-config \| include ntp` / `include clock` | сразу |
| Время синхронизировано? | `show ntp status`, `show ntp associations` | через десятки секунд |

Путать их нельзя: конфиг может быть применён и корректен, а синхронизация ещё не произошла.
Если считать отсутствие синхронизации ошибкой применения, устройство останется с несохранённым
конфигом — и это худший из возможных исходов.

## Правила безопасности при работе с парком

- **Сначала чтение, потом запись.** Массовое изменение без dry-run по всему списку — не делать.
- **Первая запись — не на рабочем ядре.**
- **Проверять результат чтением до сохранения:** `send_config_set` не подтверждает применение.
- **Сообщение об ошибке должно называть реальную причину.** «Конфиг не сохранён» и «сервер
  не синхронизировался» — разные ошибки с разным лечением.
- **Не жечь учётную запись:** для отладки — `--limit` на одном хосте и `MAX_AUTH_FAILS_IN_ROW = 1`.
- **Бэкап без проверки — не бэкап.** Сначала убедиться, что полученное похоже на конфиг,
  потом писать на диск.

## План

1. **Бэкап** — готово, проверено на парке.
2. **Diff бэкапов** (следующее) — сравнение с предыдущей датой: что добавилось, что ушло,
   запись в лог.
3. **Ротация** — сколько дней хранить `backups/`, ограничение размера `out/backup.log`.
4. **Разбор вывода** — `show interfaces status` в структуру (VLAN, режимы портов, trunk).
5. **Desired state** — целевая конфигурация в YAML, применение и сверка с фактическим состоянием.
6. **Ansible-обёртка** — отложена, отдельная фаза.
